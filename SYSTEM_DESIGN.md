### 1. What happens if we ask you to add a new feature to this later? Does your current design accommodate that, or does it need a rework? Walk through a specific feature and where it would plug in?

The design is meant to grow by adding new parts next to the old ones, not by changing what already works, and two things make that possible. First, the robots and the backend never talk to each other directly, they only talk through the broker in the middle, so a new kind of message can be introduced without either side needing to know anything new about the other. Second, the backend is built out of small independent pieces, so a new piece can be dropped in beside the rest. Take a concrete example, letting an operator send a command down to a robot, such as return to the charging dock. Today the data flows only one way, the robots report and the backend listens. A command simply adds a second, opposite flow: the backend sends the command onto a new command channel meant for that one robot, and the robot listens on that channel and acts on it. The operator triggers it through a new request the backend accepts, and if we want, the backend can remember the last command it sent so it shows up alongside the robot's state for free. Nothing about how the current state is stored or served to the dashboard has to change, so the two views still agree and none of the existing code is touched. In short the feature arrives as new code sitting beside the old code, which is exactly what a decoupled, piece-by-piece design is supposed to allow.

### 2. What happens if the number of robots grows a lot, say from eight to five hundred? What is the first thing that breaks, and why that specifically?

The first thing to break is the broker's bounded message queue, and it breaks during a backend crash, not in steady state. At eight robots the backend can be down about ten minutes before the 1000 message queue overflows; at five hundred robots the message rate is roughly 100 per second, so the same queue fills in about ten seconds, shorter than a normal deploy, after which the broker silently drops messages. It fills faster precisely because every robot keeps publishing while the consumer is absent. Close behind, aggregate bandwidth and broker memory increase steadily, and Mosquitto being single-threaded starts to saturate on connection count, so the broker itself can fall over if memory and storage were not sized for it. On the read side, GET /robots returning five hundred objects in a single response also stops being optimal and would need pagination.

### 3. What happens if bandwidth is limited and robots and the backend can only exchange a small amount of data per second? What would you change about what you send, how often, or how much detail it carries?

I would make each message smaller, send fewer of them, and carry less detail. First shrink the format: JSON is verbose, so switch to a compact binary encoding like Protobuf. Then cut redundant and low-value fields from the payload. For example, in the events.json shape the robot_id key is redundant because the topic fleet/{id}/state already identifies the robot, so it can be dropped; t can be sent as a small relative delta instead of an absolute number. Second, send only what matters: publish position at a lower cadence, and publish battery and status only when they actually change rather than every tick, so the live stream carries important events instead of a fixed heartbeat of full snapshots. The current state model already tolerates this, because the backend keeps the last value and only the changes need to travel.

### 4. What happens if a robot goes down mid task and stops responding? What should the rest of the system do about it, and how would it even find out?

The system finds out in two independent ways, and the rest of the fleet is unaffected because everything is decoupled through the broker. If the connection actually drops, the broker notices the missing keepalive after about 1.5 times the keepalive interval and publishes that robot's Last Will to fleet/{id}/status, which the backend applies and exposes as link equal to lost. If instead the robot is down but its socket is still open, no Last Will fires, so the backend's own freshness timer catches it: it compares our arrival clock, received_at, against a threshold and marks the robot stale. Either way the operator sees the robot flagged through GET /robots and the WebSocket stream, its last known state stays visible (from the retained message) but is clearly marked not fresh, and no other robot is disturbed.

### 5. What happens if the connection between a robot and the backend is slow or unreliable, and updates arrive late, out of order, or not at all for a while? What does the rest of the system see during that time, and how does it recover once the connection is healthy again?

On a flaky link we cannot trust the order that messages arrive in, so the backend never orders by arrival; it orders by the robot's own clock t using the drop rule, which ignores any message whose t is not newer than what we already hold. That means a late or reordered update with an older t is simply dropped and can never move the state backwards. Freshness, however, is judged by arrival time: received_at is our clock, and if nothing arrives for a while the robot is marked stale, meaning it is either dead or alive but not responding, which the operator sees on both the REST and WebSocket views along with the last good state. During the flaky connection time, or when a robot went down and got back up, clients keep seeing that last known state, correctly flagged as stale or lost, rather than a wrong value. Once the connection is healthy again the robot resumes publishing, the backend keeps accepting events, the first message with a newer t is applied, received_at updates, and the stale flag clears.
